# 0016 — How the website reads data and decides who sees what

- **Date:** 2026-10-11
- **Status:** Accepted in the shared platform; carried over
- **Inherited:** from the shared platform (TBD@ca7e44c, same number), adapted for this product on 2026-10-19 (English
  only; the crypto weekly e-mail added; the stock and bond tiers removed).

## Decisions

1. **One tier check, impossible to bypass by construction.** `web/lib/entitlements.ts` decides. The only function that
   reads the database (`web/lib/db.ts`) accepts only the grant that check returns, reads only that model's own
   published output tables, only its current version, and never past a free preview's date. Unit tests check the
   structure (nothing else imports the database driver; every data function goes through the check).
2. **The site reads the database as `web_reader`**, a role that can only select from the `models` schema (migration
   0003). Row-level security is on for every table, so any other non-owner role, such as the browser roles a Supabase
   project creates, reads nothing even if a schema were exposed by mistake.
3. **Every page renders per request on the server**, and API responses are `private, no-store`, so no shared cache can
   hand one tier's page to another. The build test checks that no data page is built ahead of time.
4. **Accounts are stubbed until the Supabase project exists:** every visitor is anonymous and on the free tier.
   `web/lib/viewer.ts` is the one place that changes when Supabase Auth is added. Tests act as other tiers with a
   header that works only when `ALLOW_TEST_TIERS=1` and the app is not running as production or on Vercel.
5. **E-mail follows the same rule as pages.** The weekly e-mail (`web/lib/email/`) is built through the same data
   functions, once per market and tier, so it is never personalised and never carries another tier's numbers. It is
   stricter than a page in one way: it never carries a delayed free preview, so last week's figures cannot read as
   this week's. The tier-leak suite checks its preview page (`/email/crypto`) for every model and tier.
6. **English only at launch, with no language prefix in addresses.** All text is in `web/messages/en.json` with typed
   keys (a missing key fails the build).
7. **Plain Postgres access (`pg`) rather than the Supabase JavaScript client**: the site only reads pre-computed tables
   on the server.
8. **The model registry is copied into the web app** (`web/lib/generated/registry.json`, regenerated by
   `python -m data_platform.models.registry export-web`; CI fails if it is stale), together with the method pages,
   disclaimers and calendars, so the web app never reads files outside `web/` on Vercel.
9. **npm runs with `legacy-peer-deps`** (`web/.npmrc`): npm's resolver crashes on this dependency tree; every peer the
   app needs is listed explicitly instead.
